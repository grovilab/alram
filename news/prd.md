# PRD: 알람 발생 시 최신 뉴스 브리핑 기능

> 참고 문서: [최근뉴스_기술명세서.md](../최근뉴스_기술명세서.md)

## 배경 및 목표

현재 알람 웹앱은 설정한 시각에 소리로만 사용자를 깨운다. 여기에 "최신 뉴스 검색 + 음성 낭독" 기능을 추가하여, 알람이 울릴 때(또는 사용자가 원하는 시점에) 최신 뉴스 5건을 화면에 보여주고 음성으로 들려줌으로써 아침 루틴에서 뉴스 확인 단계를 자동화하는 것이 목표다.

기술 명세서 상 제안된 스택은 Supabase(Edge Function + Postgres) + React이나, 본 PRD는 제품 요구사항을 정의하는 문서이며 실제 구현 스택(React 전환 여부, Supabase 채택 여부 등)은 Open Questions에서 별도로 확인한다.

## 사용자 스토리

- 사용자로서, 아침 알람이 울릴 때 오늘의 주요 뉴스 5건을 바로 화면에서 확인하고 싶다.
- 사용자로서, 뉴스를 눈으로 읽을 여유가 없을 때 음성으로 낭독을 듣고 싶다.
- 사용자로서, 관심 있는 뉴스 원문을 클릭해 출처 페이지로 이동하고 싶다.
- 사용자로서, 뉴스 브리핑 기능에 문제가 생기더라도 알람 자체(소리)는 반드시 정상적으로 울려서 늦잠을 자지 않기를 원한다.
- 사용자로서, 알람과 무관하게 필요할 때 수동으로 최신 뉴스를 다시 불러오고 싶다.

## 기능 요구사항

1. 알람이 울리는 시점(또는 그에 준하는 트리거)에 최신 뉴스 5건을 조회하여 화면에 카드 형태로 표시한다.
2. 각 뉴스 카드에는 제목, 요약(또는 짧은 설명), 출처, 원문 링크를 표시한다.
3. 각 뉴스 카드에 "🔊 듣기" 버튼을 제공하여 브라우저 내장 음성 합성(Web Speech API, `lang='ko-KR'`)으로 해당 뉴스를 낭독한다.
4. 뉴스 원문 링크 클릭 시 새 탭에서 출처 페이지로 이동한다.
5. 뉴스 조회가 실패하거나 결과가 0건인 경우, 사용자에게 실패/빈 상태를 명확히 안내하는 UI를 표시한다(예: "뉴스를 불러오지 못했습니다").
6. 뉴스 API 호출은 클라이언트가 아닌 서버 사이드 프록시(예: Edge Function)를 통해서만 이루어진다.

## 비기능 요구사항 (보안 최우선)

- **네이버 API 키(Client ID/Secret)는 프론트엔드에 절대 노출하지 않는다.** 클라이언트 번들, 네트워크 요청, 소스맵 등 어떤 경로로도 키가 노출되어서는 안 되며, 반드시 서버 사이드(Edge Function 등) 환경 변수에만 보관하고 클라이언트는 서버 프록시를 통해서만 뉴스 데이터를 받는다.
- **뉴스 데이터는 DB에 저장하지 않고 매 요청마다 실시간으로 조회한다.** 기술 명세서에서 제안한 `news_cache` 테이블 및 주기적 캐싱/스케줄링(pg_cron 등)은 본 제품 요구사항과 상충하므로 채택하지 않는다. 서버 프록시는 매 요청 시점에 외부 뉴스 API를 직접 호출하여 그 결과를 그대로 반환하고, 별도로 영속 저장하지 않는다.
- **뉴스 브리핑 기능이 실패해도 알람 소리 자체는 반드시 울려야 한다.** 뉴스 조회, 낭독(TTS), 렌더링 등 어떤 단계에서 오류가 발생하더라도 알람의 핵심 기능(정해진 시각에 소리로 알리는 것)은 이 기능과 독립적으로 동작해야 하며, 뉴스 기능의 예외가 알람 트리거 로직을 막거나 지연시켜서는 안 된다.
- 외부 뉴스 API에 대한 과도한 호출을 막기 위한 요청 빈도 제한(rate limiting) 또는 최소한의 재시도/타임아웃 정책을 서버 프록시 단에 둔다(단, 이는 결과를 저장하는 캐싱과는 구분되는 호출 보호 조치).
- 서버 프록시(Edge Function 등)와 클라이언트 간 통신은 HTTPS로만 이루어진다.
- 뉴스 낭독(Web Speech API)은 브라우저 내장 기능만 사용하며, 별도 음성 API 키가 필요한 대체 수단(클로바 보이스, Google Cloud TTS 등)은 이번 범위에서 도입하지 않는다.

## 범위 제외 (Out of Scope)

- 뉴스 데이터의 DB 캐싱, 주기적 배치/스케줄링 갱신(pg_cron 등) — 비기능 요구사항에 따라 실시간 조회 방식만 사용하므로 제외.
- 네이버 클로바 보이스, Google Cloud TTS 등 유료/별도 키가 필요한 음성 합성 서비스 도입.
- 사용자별 뉴스 개인화(관심사 기반 추천, 로그인/계정 연동).
- 뉴스 댓글, 공유, 북마크/저장 등 부가 소셜 기능.
- 다국어 뉴스 지원(우선 한국어 뉴스만 대상).
- 뉴스 이외의 다른 브리핑 콘텐츠(날씨 음성 브리핑 등, 현재 화면에 있는 기온/습도 텍스트 표시 기능과의 통합)는 이번 범위에서 다루지 않는다.

## Open Questions

- 검색 키워드/카테고리가 아직 확정되지 않았다. "최신 뉴스"의 기준이 특정 키워드 검색인지, 특정 카테고리(속보/정치/경제 등)인지, 아니면 키워드 없이 네이버 뉴스 API의 기본 최신순 결과인지 결정 필요.
- 사용할 뉴스 소스 API가 네이버 뉴스 검색 API로 확정된 것인지(비기능 요구사항에는 "네이버 API 키"로 명시되어 있으나, 기술 명세서는 "네이버 뉴스 API, NewsAPI 등"으로 복수 후보를 언급함) 확인 필요.
- 실제 구현 스택을 기술 명세서대로 React + Supabase Edge Function으로 전환할지, 현재의 vanilla HTML/CSS/JS 정적 구조를 유지하면서 별도의 경량 서버 프록시(예: 서버리스 함수 1개)만 추가할지 결정 필요.
- "알람이 울리는 시점"에 뉴스 브리핑을 자동 트리거할지, 알람 종료 후/스누즈 화면 등 어느 시점에 노출할지 UX 플로우 확정 필요.
- 서버 프록시 호출에 대한 구체적인 rate limit 수치(횟수/시간 단위) 및 실패 시 재시도 횟수 기준 미정.
- 오프라인 상태이거나 서버 프록시 자체에 접근할 수 없는 경우의 사용자 안내 문구/UX 미정.

## 성공 기준

- 알람이 울리는 시점에 최신 뉴스 5건이 정상적으로 화면에 표시되는 비율이 측정 가능해야 하며, 정상 동작 시 5건이 누락 없이 노출된다.
- 네이버 API Client ID/Secret이 클라이언트에서 확인 가능한 어떤 경로(브라우저 개발자 도구, 네트워크 탭, 소스 코드 등)로도 노출되지 않음을 코드 리뷰 및 네트워크 점검으로 확인한다.
- 뉴스 데이터가 별도 DB/테이블에 영속 저장되지 않고, 매 요청이 실제로 외부 API를 호출함을 확인한다(응답에 캐시 여부가 드러나지 않아야 함).
- 인위적으로 뉴스 API 실패(네트워크 차단, 잘못된 키 등)를 재현했을 때도 알람 소리가 설정된 시각에 정상적으로 울리는지 테스트로 검증한다.
- "🔊 듣기" 버튼 클릭 시 한국어 음성으로 뉴스 내용이 낭독되는지 확인한다.
